**ITCS 6190/8190 - Cloud Computing for Data Analysis - Fall 2026**

In Hands-on L6 you wrote four DataFrame queries over a clean dataset. This week you answer
four questions about a small social network, two of them in **Spark SQL** over temporary

`posts.csv`, 5,000 rows, one per post:

| column            | type      | example                 | notes                              |

| column      | type    | example         | notes                      |

## The tasks

`main.py` loads the two files with explicit schemas and registers them as the temporary
views `posts` and `users`. The four tasks are laid out as functions that return a
DataFrame; the docstring of each one states the exact columns, ordering and rounding. The
output of each task is written to `shared-folder/output/taskN/` as a single CSV file.

**Task 1. Hashtag trends (DataFrame API).** The `hashtags` column holds a comma-separated
list. Split it, `explode` it into one row per hashtag, normalize with `lower` and `trim` so
that `#Tech`, `#TECH` and `#tech` are the same hashtag, and count. Output: `hashtag, count`,
the ten most frequent, ordered by count descending, then hashtag.

**Task 2. Engagement by age group (Spark SQL, and the DataFrame twin).** In **one**
`spark.sql(...)` call, join `posts` with `users` and compute, per age group, the number of
posts and the average likes and retweets, rounded to two decimals. Output: `age_group,
posts, avg_likes, avg_retweets`, ordered by `avg_likes` descending. Then write the same
query with the DataFrame API in `task2_engagement_by_age_df`; `main.py` prints the
physical plan of both for the report.

**Task 3. Sentiment versus engagement (Spark SQL).** In **one** `spark.sql(...)` call,
classify each post with a `CASE` expression: `Positive` if `sentiment_score` is greater
than 0.3, `Negative` if it is less than -0.3, `Neutral` otherwise; then compute the number
of posts and the average likes and retweets per category, rounded to two decimals. Output:
`sentiment, posts, avg_likes, avg_retweets`, ordered by `sentiment`.

**Task 4. Top verified users (DataFrame API).** For verified users only, the total likes,
total retweets and `reach = total_likes + total_retweets` over all their posts. Output:
`username, total_likes, total_retweets, reach`, the top five by reach descending, then
username.

Tasks 2 and 3 must be SQL strings passed to `spark.sql`; tasks 1 and 4 must use the
DataFrame API. No RDD operations, no `collect()` followed by Python loops, no pandas.

## Steps

### 1. Make your own copy of this repository

On the repository page, click the green **Use this template** button, then
**Create a new repository**. Name it `ITCS6190-H9-<your-name>` and set the visibility to
**Public**. Do not fork and do not clone this repository directly. Clone *your* repository
and work in it.

### 2. Generate your data

```bash
python3 datagen.py <your student ID>
```

Two files appear under `shared-folder/input/`. Open `posts.csv` and look at the `hashtags`
column: the same hashtag appears in several spellings. Write your seed in `REPORT.md`; the
grader regenerates your data from it.

Without Python on your machine, start the cluster first (step 3) and run the generator in
the master container, which has Python 3:

```bash
docker cp datagen.py spark-master:/opt/spark/work-dir/shared/
docker exec spark-master python3 /opt/spark/work-dir/shared/datagen.py <your student ID> \
  /opt/spark/work-dir/shared/input
```

### 3. Start the cluster

```bash
docker compose up -d
```

Open <http://localhost:8080> and check that the master lists two workers in state ALIVE.

**In a GitHub Codespace**, start the cluster with the other compose file instead, as in
Hands-on L5 and L6:

```bash
docker compose -f docker-compose.codespaces.yml up -d
```

Inside a Codespace, traffic between containers on a Compose network can be dropped, so the
workers never register with the master and every job waits forever with `Initial job has not
accepted any resources`. That file puts the whole cluster on one network to avoid it.
Everything else is the same, except that `docker compose down` in step 7 also needs the
`-f docker-compose.codespaces.yml` flag.

### 4. Run `main.py` as it is

```bash
docker cp main.py spark-master:/opt/spark/work-dir/

docker exec -it spark-master /opt/spark/bin/spark-submit \
  --master spark://spark-master:7077 \
  /opt/spark/work-dir/main.py \
  /opt/spark/work-dir/shared/input \
  /opt/spark/work-dir/shared/output
```

The program loads the two files, prints the schema and the row counts, registers the views
and reports each task as "not implemented yet".

### 5. Fill in the tasks, one at a time

Edit `main.py` on your machine. After each change, repeat the `docker cp` and the
`spark-submit` from step 4. A task whose function still returns `None` is skipped, so the
file always runs. Results are printed in the terminal (`show`) and written under
`shared-folder/output/`; outputs are overwritten on each run.

The SQL tasks are easiest to develop in the `spark-sql` shell, which takes SQL statements
directly (end each one with a semicolon):

```bash
docker exec -it spark-master /opt/spark/bin/spark-sql --master spark://spark-master:7077
```

There the views do not exist yet, so create them from the files first:

```sql
CREATE OR REPLACE TEMPORARY VIEW posts USING csv
  OPTIONS (path '/opt/spark/work-dir/shared/input/posts.csv', header 'true', inferSchema 'true');
CREATE OR REPLACE TEMPORARY VIEW users USING csv
  OPTIONS (path '/opt/spark/work-dir/shared/input/users.csv', header 'true', inferSchema 'true');
SELECT * FROM posts LIMIT 5;
```

For the DataFrame tasks, the PySpark shell works as in the previous hands-ons:

```bash
docker exec -it spark-master /opt/spark/bin/pyspark --master spark://spark-master:7077
```

### 6. Compare the two plans

When both versions of task 2 are done, `main.py` prints their physical plans one after the
other. Read them bottom up: two `FileScan csv`, the join, the aggregation in two steps with
an `Exchange` between them, the sort. Open <http://localhost:4040> while the program runs
and find the two queries in the **SQL / DataFrame** tab; they draw the same diagram.

### 7. Stop the cluster

```bash
docker compose down
```

## Troubleshooting

- **`no configuration file provided: not found`**: you are not in the folder that contains
  `docker-compose.yml`. `cd` into your repository first.
- **`python3: can't open file '/opt/spark/work-dir/main.py'`**: the `docker cp` in step 4 is
  missing, or you edited `main.py` and forgot to copy it again.
- **`Path does not exist: .../input/posts.csv`**: run `datagen.py` first, and check that the
  files are under `shared-folder/input/` on your machine.
- **`[TABLE_OR_VIEW_NOT_FOUND] The table or view posts cannot be found`**: in `main.py` the
  views are created before the tasks run, so this means a typo in the name; in the
  `spark-sql` shell it means you have not created the views (step 5).
- **`[UNRESOLVED_COLUMN]` on `avg_likes` in `ORDER BY`**: the alias is missing or spelled
  differently in the `SELECT` list.
- **`AnalysisException: ... Reference 'user_id' is ambiguous`**: after a join with
  `p.user_id = u.user_id` the column appears twice; qualify it (`u.user_id`) or, in the
  DataFrame API, join with the string form `join(users, "user_id")`.
- **Task 1 counts `#tech` and `#Tech` separately, or has spaces in hashtags**: apply
  `lower` and `trim` after `explode`, not before `split`.
- **Results in a different order than specified**: `show()` on an unordered DataFrame prints
  rows in partition order. Add the `ORDER BY` or `orderBy` from the task description.
- **`Permission denied` when writing the output (Linux)**: the containers run as user
  `spark` (uid 185). Run `chmod -R a+rwX shared-folder` and try again.
- **Job accepted but no progress, `Initial job has not accepted any resources`**: a PySpark
  or spark-sql shell is still open and holds the cores. Close it.
- **The master page shows no workers**: wait a few seconds and refresh; if they never appear,
  `docker compose logs spark-worker-1`.
